# 桌宠 TTS 语音方案（待实现）

> 状态：方案 / 评审修订（2026-10-21 记录，未开工）
> 关联：`docs/pending/桌宠结合设计方案.md`（P0–P9 已完成）· 后续项见 `docs/pending/桌宠时间驱动主动开口方案.md`

## 0. 评审结论

这份方案的技术选型保留：第一版使用 WebView2 自带的本地 `speechSynthesis`，不引入云端 TTS、音频播放器或新的密钥配置。

需要调整的是接入方式：TTS 不能只监听 `pet-say-done`。当前桌宠还有本地台词、自动点评失败后的本地回退、通知气泡和即将加入的时间问候；只监听 AI 完成事件会导致同一句话能看见却听不到，或者通知到达时仍有上一句在播放。因此增加一个轻量的**语音仲裁层**，统一决定“哪一类内容可以读、何时打断、是否只显示气泡”。TTS 只负责最终输出声音，不负责触发主动行为。

第一版的默认体验应是：**桌宠可以显示内容，但不会突然发声；用户开启声音后，仍只朗读被明确标记为可朗读的内容。**

## 1. 为什么做

现在桌宠只会**看**——气泡里的字得自己读。想让它像真的在旁边，得能出声。

但这件事的风险比看起来大：**主动出声比被动显示侵入性强得多**。突然在办公室冒出人声，比屏幕角落多个气泡严重得多。所以本方案的全部重点不在「怎么发声」，而在「怎么确保它不乱出声」。

## 2. 实测结论（选型依据）

在真实运行的 WebView2 里用 CDP 探针实测，不是查文档推演：

```text
speechSynthesis            可用，且真的发声（utterance-start 事件确实触发）
中文音色                    3 个，全部 localService（不联网、无依赖、无需 key）
  Microsoft Huihui   / zh-CN / local   女声，最自然
  Microsoft Kangkang / zh-CN / local   男声
  Microsoft Yaoyao   / zh-CN / local   女声，偏童声
音色加载                    异步：首次 getVoices() 返回 0，约 2.5s 后才有 3 个
```

**结论：不需要加任何依赖、不需要联网、不需要 API key。** 前端 `window.speechSynthesis` 即可满足。

复现方法：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` 启动，连上 `pet=1` 页面的 CDP，求值 `speechSynthesis.getVoices()`，注意要等 `voiceschanged`。

## 3. 方案

### 3.0 统一语音管线

新增 `src/pet/usePetSpeak.ts`，并在其上方收敛一个前端语音仲裁入口（可以先放在同一 hook 内，后续再拆文件）。所有可能产生文字的地方都提交一个 `SpeechIntent`，而不是直接调用 `speechSynthesis`：

```ts
type SpeechIntent = {
  source: 'manual' | 'auto' | 'time' | 'notice' | 'local';
  text: string;
  priority: 'notice' | 'manual' | 'proactive' | 'ambient';
  speakable: boolean;
  sessionId?: number;
};
```

仲裁层负责以下事情：

- 统一检查桌宠是否可见、是否全屏、是否拖拽、是否在输入或小游戏中；
- 统一检查静默时段、当天主动次数、用户“今天别说话了”状态；
- 按优先级打断：通知 > 用户主动对话 > 时间主动内容 > 自动点评 / 普通台词；低优先级内容不能打断用户正在听的回答；
- 保证同一时间最多一个 utterance，不排队播放已经过期的内容；
- 将“显示气泡”和“播放语音”分开。关闭 TTS 时气泡照常显示，TTS 不可用时也不影响桌宠功能。

`pet-say-done` 仍然是 AI 正文的输入来源，但本地台词和时间问候也必须经过同一个入口。这样 AI 请求失败回落到本地台词时，仍能按同一规则决定是否朗读。AI 事件需要把 `pet-say-start` 中的 `trigger` 按 `sessionId` 保留到完成态，或在 done 事件中补带来源；不能用“最近一次触发类型”的全局变量关联，因为新会话会覆盖它。

### 3.1 `usePetSpeak.ts` 的职责

在 `pet-say-done` 拿到**最终正文后**提交一次朗读；本地台词则在 `showBubble` / 时间问候确定最终文本后提交。不要在流式 delta 到达时朗读。

不采用「边流式边读」：流式是逐字到达，边收边读会一个字一个字往外蹦，还会反复重读同一句。等整段结束再读，延迟只有几秒，体验反而干净。

### 3.2 读什么

| 决策点 | 选择 | 理由 |
|---|---|---|
| 读的内容 | 只读最终正文，绝不读思考链、工具状态、Markdown 代码块、URL | 思考链和工具状态是中间态；语音应复用气泡侧的正文判定，但还要做一层适合朗读的文本清洗 |
| 自动内容长度 | 默认 50～60 个汉字 | 时间问候和自动点评应控制在十几秒内；超长内容直接截断，不追加“后面不念了”这类元话术 |
| 用户主动对话长度 | 默认最多 120 个汉字 | 用户主动发起的问题可以比独白更长；更长的回答只在气泡中显示，避免读几十秒 |
| 默认开关 | **关闭** | 突然出声会吓人；静音办公场景更明显 |
| 音色匹配 | 优先 `lang` 以 `zh` 开头且 `localService=true` 的音色；设置保存 `voiceURI`，同时保留 name/lang 回退 | 音色名随系统语言变化，`voiceURI` 找不到时按语言和本地服务回退到第一个可用音色 |
| 打断 | 由语音仲裁层按优先级调用 `cancel()` | 不能简单地“任何新消息都打断”，否则低优先级彩蛋会截断用户回答 |
| 静默条件 | 桌宠隐藏 / 全屏 / 拖拽中 / 输入框或小游戏打开 / 默认深夜 23–5 点 / 用户当天静音 | 看不见的窗口在说话很诡异；忙碌时应让位给当前操作 |

内容来源的默认口径：

| 来源 | 默认显示气泡 | 默认朗读 | 说明 |
|---|---:|---:|---|
| 用户主动对话 | 是 | TTS 开启后可读 | 用户正在等待答案，优先级最高 |
| 事件自动点评 | 是 | **默认不读** | 仍可在设置中单独允许自动内容朗读 |
| 时间主动问候 | 是 | **默认不读** | 与主动开口开关分开，避免打开 TTS 后突然增加声音 |
| 随机彩蛋 / 点击台词 | 是 | 否 | 这些内容频率高，全部朗读会很快变成噪音 |
| 系统通知 | 是 | 否 | 通知到达时打断当前普通语音；若未来要读通知，应做独立开关 |

### 3.3 设置项

`src-tauri/src/models.rs` 的 `Settings` 新增（全部 `Option`，默认 `None`）：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `pet_tts` | `Option<bool>` | `None`（=关） | 总开关 |
| `pet_tts_auto` | `Option<bool>` | `None`（=关） | 是否朗读事件自动点评 |
| `pet_tts_proactive` | `Option<bool>` | `None`（=关） | 是否朗读时间主动内容 |
| `pet_tts_voice` | `Option<String>` | `None`（=自动取第一个本地 zh） | 优先保存 `voiceURI`；失效时按中文 + 本地音色回退 |
| `pet_tts_rate` | `Option<f32>` | `None`（=1.0） | 语速，夹到 0.8–1.4 |
| `pet_tts_volume` | `Option<f32>` | `None`（=0.8） | 音量，夹到 0–1 |

`pet_tts` 是总静音开关；自动点评与时间主动内容分别由 `pet_tts_auto` / `pet_tts_proactive` 控制。用户主动对话在总开关打开后可朗读；随机彩蛋、点击台词和系统通知仍不读。下发路径与现有 `pet_*` 字段一致：`pet_status` 与 `apply_settings` 的 `pet-update` 事件各带一份。设置页加在桌宠分区，与 AI 档位相邻但说明清楚“朗读设置不会启用自动发言”。

### 3.4 音色选择的交互

设置页下拉只列 `lang` 以 `zh` 开头且 `localService=true` 的音色。**若列表为空，明确显示「未检测到本地中文语音包」并禁用开关**，而不是给一个空下拉让人猜。关闭总开关时不启动朗读；设置页需要显示音色时，等用户进入设置分区后再枚举音色，不要在宠物启动时为 TTS 做无用初始化。

## 4. 必须处理的坑

1. **音色异步加载** —— 不能在组件挂载时直接 `getVoices()[0]`，那时是空数组。必须监听 `voiceschanged`，并设超时兜底（约 3 秒），避免某些环境下该事件永不触发导致功能死等。
2. **系统没装中文语音包** —— `voices` 为空时**优雅降级为不读**：不报错、不弹窗、不写错误日志刷屏。中文语音包在部分精简版 Windows 上是真的没有。
3. **窗口隐藏时主动取消** —— 不依赖 WebView2 是否暂停语音。收到 `pet-update.visible=false`、`document.hidden` 或全屏事件时主动 `speechSynthesis.cancel()`，重新显示后不恢复已经被截断的旧句子。
4. **不要与通知气泡抢** —— 通知（`pet-notice`）是操作结果，比闲聊台词重要。通知出现时取消普通台词；通知本身第一版只显示，不朗读。
5. **文本清洗** —— 朗读前移除 Markdown 标记、代码块、链接、连续空白和过长的英文标识；空文本、纯符号和只有思考链的消息直接跳过。
6. **输出设备变化** —— 系统切换耳机、蓝牙或远程桌面后可能出现无声；设置页提供“试听”按钮，失败时只提示音色不可用，不影响气泡。

## 5. 已知局限（先说清）

这三个是 SAPI 时代的音色，**机械感明显**。不要期待豆包 / Azure 那种自然度，写进文档免得实现完才发现落差。

想更好只有两条路，都要付代价：

| 升级路径 | 代价 |
|---|---|
| Edge TTS（微软在线神经音色） | 需联网 + 逆向 WebSocket 协议，不稳定因素多，断网即失效 |
| 本地 Piper / VITS | 要打包 50MB+ 模型，首次加载慢，安装包显著变大 |

**建议：先用系统音色把完整链路做对（开关 / 仲裁 / 打断 / 静默 / 降级），确认日常真的会用，再考虑换音色。** 音色是最后一步，不是第一步。

## 6. 不做的

- 不做云端 TTS（违背「不新增网络外发」的既有红线，见 AGENT.md §5.5）
- 不做语音输入 / 语音对话（成本高，且与「桌宠」定位不符）
- 不做口型同步（素材是 WebM，没有口型帧）
- 不做「边流式边读」
- 不让随机彩蛋、点击回应和所有系统通知默认出声
- 不把时间主动开口直接绑定到 AI 请求；时间问候优先使用本地台词

## 7. 验收标准

1. 关闭开关时，任何迹象都没有：不说话、不加载音色、不写日志
2. 开启后让桌宠说一句 → 3 秒内开始出声，气泡与语音大致同步
3. 说长句期间再发一条 → 前一句立即停，不叠音
4. 把 Windows 中文语音包移除（或模拟 `getVoices()` 返回空）→ 功能自动降级，不报错不弹窗，设置页给出提示
5. 深夜 23 点后不朗读
6. 桌宠隐藏时不朗读
7. 通知气泡到达时，台词朗读让位
8. 自动点评和时间问候在未单独允许时只显示气泡、不播放声音
9. AI 请求失败回落本地台词时，朗读仲裁仍能正确执行，不出现“气泡有字但规则失效”

## 8. 成本

约 1.5～2 天（含语音仲裁、设置页 UI、来源接线、降级路径与逐条实测）。

## 9. 实现顺序建议

先做「读一句固定文本」的最小闭环（验证音色可用、能打断），再做语音仲裁与文本清洗，随后接本地台词和 `pet-say-done`，最后接时间主动内容。顺序反过来的话，触发规则和音频输出会各自形成一套互相冲突的静默/打断逻辑。
