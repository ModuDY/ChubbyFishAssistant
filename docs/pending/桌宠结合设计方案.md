## 0. 一句话

在现有 Tauri 2 单窗口应用里**新增一个透明置顶的第二窗口**，前端按 URL 参数分流渲染"大肥鱼"，让它实时化身本工具的签到 / 积分 / 网关运行状态；台词与对话能力**复用已有本地 axum 网关**，不新建后端。

---

## 1. 前置事实修正（重要）

方案必须建立在真实代码结构上，先纠正三个容易想当然的前提：

| 想当然 | 实际情况 |
|---|---|
| "项目里有 AI 聊天助手，把宠物接进去" | **没有聊天 UI，也没有 LLM 会话循环**。"AI 助手"是产品品牌名（v3.0.0 由"Trae Work 助手"迁移而来）。 |
| "需要新建窗口框架 / 事件系统" | **都已具备**：Tauri 2 多窗口、系统托盘、全局事件总线、SQLite 存储、本地 API 网关（axum，`127.0.0.1:7864`，OpenAI/Anthropic/Codex 三协议）。 |
| "宠物要自己抓数据" | **不必**。现有业务事件是**全局广播**（`app.emit` 级），宠物窗口直接 `listen` 即可，零中转、零轮询。 |

因此本方案**不是"接入现有助手"，而是"给工具加一个状态化身"**——也正好对应确认的 **先 A 后 B** 路线。

### 2.5 上游工程经验（`dsh-pet-indesktop` 的可迁移结论）

这是本次核查最有价值的部分——**上游用 Qt 踩过的坑，多数在 WebView2 上同样成立**，能让我们少走弯路：

| 上游做法 / 结论 | 对我们的意义 |
|---|---|
| **不用 `<video>` 直播，而是预解码成帧序列**（`frameseq_provision.py` 136 KB / `frameseq_clip.py` 47 KB / `decode_fanout.py` 32 KB / `frame_cache.py`） | ⚠️ **直接动摇了我们"`<video>` 播 WebM"的首选方案**——上游宁可自己写 200+ KB 帧序列供给与缓存代码，也不用播放器直接播。**原因需在 P0 验证**（很可能是透明视频逐帧解码/跳帧控制/首帧预热不可控） |
| **帧序列缓存 + 优先预热**：素材热加载、`predictive_prewarm.py` 前瞻预热，避免切动作时卡顿 | 对应我们的"切状态不能卡"。若走视频方案，需用**双 `<video>` 预加载交替**或提前 `preload` |
| **懒加载 + 不预载全部** | 106 个动作不必全量打包内联 |
| **隐藏时暂停视频解码与活动定时器**（`memory_trim.py`、`gui_stall_sampler.py`）；隐藏时 CPU 接近 0 | 我们的 `pet` 窗口**不可见时必须停播放**，否则纯烧 CPU |
| **状态优先级聚合**：`attention > error > working > thinking > idle` | 比我们"新事件抢占"更严谨，**直接照搬**（见 §6.1） |
| **审核与提问为"绕提示气泡"**（另开窗口），与 `attention` 状态解耦 | 我们的气泡也应与动作状态解耦 |
| **单实例闸门** `overlay_instance_gate.py`（8.4 KB） | 我们已有 `tauri_plugin_single_instance`，无需重复 |
| **单独的点击穿透模块** `platform_passthrough.py`（16 KB）+ 按平台拆分 `platform_win.py` / `platform_mac.py` | 印证穿透是**独立且跨平台差异大**的模块 → P0 **不做**是正确决策 |
| **禁点击音效抑制**：穿透激活时不播点击音效，且"移动窗口不被屏幕边缘卡住" | 若将来做穿透，必须一并处理 |
| **音频播放器兼容**用 `papay` / `apapay` 避免静音超时 | 若加音效需注意 |
| **配置文件按"槽位"管理** `config.json` / `config-slot-N.json`，升级时 `config.pre-slot0-migration.bak` 备份 | 我们的 `Settings` 迁移思路可借鉴：**升级前先备份** |
| **只做状态标记、不 `self.affect()`**（影响最小） | 我们的宠物窗口也应**只读事件、不改业务状态** |
| **全局项写在主配置、影响所有宠物**；单宠物项写各自 `config-slot-N.json` | 对应我们：`pet_*` 全局设置 vs 多宠物场景 |
| **AI 对话走 OpenAI Chat Completions 兼容**，支持 SSE 流式/多轮/非流式/停止生成/失败重试 | ✅ **印证我们 P3 复用网关（OpenAI 协议）的路线正确** |
| **API Key 优先系统钥匙串**，不可用时回退配置文件 | 我们复用现有网关，**根本不需要在宠物侧另存 Key**（优势） |
| **Markdown 渲染**（表格/代码块/列表），HTML 按字面显示不渲染 | P3 气泡若显示 AI 回复，需做最小 Markdown 白名单渲染 |
| **`看屏幕` 截图仅在内存处理并直接发给模型，不写本地、不存副本** | ⚠️ **与我们"零外发"红线直接冲突**——上游此功能我们**不做**（见 §12） |
| **音乐播放器/歌词/占卜/节日等大量扩展** | 属 P4 之后，本方案不涉及 |

**结论**：上游的**素材与规格可以照抄**，**生命周期/状态/降级策略可以直接借鉴**，但**外围功能（看屏幕、音乐、占卜）不要引入**——既有红线冲突，也会严重膨胀工作量。

## 3. 总体架构

**单进程，双窗口，共享事件总线。**

```
Tauri 进程（ai-work-assistant.exe）
├── WebView "main"          ← 现有 UI，不动
│     └── App.tsx（TitleBar + Sidebar + 页面切换）
├── WebView "pet"（新增）    ← 透明 / 无边框 / 置顶 / 不进任务栏 / 不可缩放
│     └── index.html?pet=1 → PetRoot（PetSprite 渲染 + PetBubble + 状态机）
├── 事件总线（已有，全局广播）
│     ├─ checkin-progress / wb-checkin-progress / qoder-checkin-progress
│     ├─ wb-credits-updated / proxy-log / switch-progress / switch-done
│     └─ （新增）pet-state、pet-say
├── 托盘（已有）→ 新增「显示/隐藏桌宠」菜单项
├── SQLite / conf/app_settings.json（已有）→ 新增 pet_* 字段
└── axum 网关 127.0.0.1:7864（已有）→ 作为 P3 台词/对话通道
```

**关键设计决策与理由**：

| 决策 | 选择 | 理由 |
|---|---|---|
| 窗口创建方式 | **声明式**（写进 `tauri.conf.json`，`visible:false` 后运行时 show/hide） | 与现有 `main` 窗口写法一致，权限 `windows` 引用天然生效，避免在 `main.rs` 里写 builder |
| 前端代码复用 | **复用同一份 `index.html`，`?pet=1` 分流** | 零新增构建入口（`vite.config.ts` 未配置多入口，新增会牵动 `beforeBuildCommand` / `frontendDist`） |
| 渲染载体 | **`<video>` 播 WebM（VP9 alpha）**——已实测确定 | 实测见 §8.3.1：alpha 完整保留、首帧 3~51ms、窗口透明生效、页面渲染正常。上游的帧序列方案在 WebView2 上**不需要复制** |
| 宠物状态来源 | 直接 `listen` 现有事件 | 事件已是全局广播，**不需要 Rust 侧转发层** |
| LLM 通道（P3） | Rust 命令内部复用网关 | API Key 不出 Rust、**不改 CSP**、网关未启动可兜底本地台词池 |

## 4. 窗口设计（落点）

### 4.1 配置改动

在 `src-tauri/tauri.conf.json` 的 `app.windows` 数组**追加**第二项（现有 `main` 项不动）：

```
label: "pet"
url: "index.html?pet=1"
width: 300, height: 360, resizable: false
decorations: false, transparent: true, shadow: false
alwaysOnTop: true, skipTaskbar: true, focus: false
visible: false           // 启动不显示，由设置/托盘控制
```

> 现存事实：`main` 窗口在 `tauri.conf.json` 中声明（`label: "main"`，`decorations:false`，`maximized:true`），`main.rs` 只做"程序化最大化兜底 + 托盘 + 关闭即退出"的逻辑。沿用同一模式。

### 4.2 前端分流

`src/main.tsx` 是唯一渲染入口（当前直接渲染 `App`）。改造为：

```
读 location.search → 含 pet=1 ?
  是 → 渲染 <PetRoot />
  否 → 渲染 <App />（现有逻辑）
```

**必须在 PetRoot 分支跳过 `useAppStore.init()`**：

- 现有 `App.tsx` 的 `useEffect` 会调 `init()`，拉全量账号 / 分组 / 积分 / 快照体积统计；
- 桌宠窗口**不需要这些**，跑一遍纯属浪费（尤其快照体积统计是重 IO，见 `AGENT.md` §5 的 profile_list 性能记录）；
- 桌宠只订阅**事件**，不依赖 store 的业务数据。

### 4.3 窗口行为细则

| 行为 | 实现 |
|---|---|
| 位置记忆 | 启动时读 `settings.pet_x/pet_y` → `setPosition`；拖拽结束后写回（**去抖 500ms**，避免 `Moved` 事件高频落盘） |
| **点击热区** | **只覆盖角色可见包围盒**（P0 实测修正）：素材画布 640×360、角色只占中间一块，若根节点收事件则"点旁边一大片空白也触发动作"。做法：首帧解码后采样 alpha（160×90、阈值 64、延迟 400ms 取稳定帧）求包围盒 → 反算窗口百分比注入独立 `.pet-hit`，根节点 `pointer-events:none` |
| **气泡锚点** | 底边 = 角色包围盒顶部 + 8px（`bottom: calc(100% - top% + 8px)`）。原实现固定在窗口 `top:6px`，实测高出角色头顶约 200px |
| 拖拽 | 角色热区 mousedown → `getCurrentWindow().startDragging()`（需权限，见 §5）；阈值 5px 区分点击与拖拽 |
| 双击 | 呼出并聚焦主窗口（复用 `main.rs` 的 `show_main_window`，经新增命令 `pet_focus_main`） |
| 右键菜单 | 触发主窗口托盘已有的动作：一键签到 / 启停网关 / 打开设置（复用现有 `start_checkin_core` 等入口，**不重复实现**） |
| 缩放 | `settings.pet_scale`（0.6~1.5），改窗口尺寸 + CSS 缩放 |
| 置顶抢 z-order | Windows 下置顶窗可能与全屏应用冲突；可参考 dsh-pet 的 `topmost-watchdog` 思路，**做降级**（见 §8 风险） |

### 4.4 透明底 CSS

现有 `src/index.css` 已设置 `html, body, #root { height: 100% }`、`body { margin: 0 }`——这对普通窗口是对的，但**透明窗口会出问题**：`body` 若带背景色，透明就废了。

处理：**不改全局 CSS**，在宠物根节点作用域内显式声明：

- `html.pet-root, body.pet-root, body.pet-root #root` → `background: transparent`
- `overflow: hidden`，禁滚动条，禁 `::selection`
- 主题变量（`data-theme` / `dark`）**不参与**——宠物底色必须透明，不能跟随主题

## 5. 权限设计（落点）

**现状（关键约束）**：`src-tauri/capabilities/default.json` 的授权是**按窗口 label 限定**的——`"windows": ["main"]`。**宠物窗口默认什么权限都没有**，必须新增一份 capability。

新增 `src-tauri/capabilities/pet.json`：

```
identifier: "pet"
windows: ["pet"]
permissions: [
  core:default,
  core:window:allow-start-dragging,   // 拖拽
  core:window:allow-set-position,     // 位置记忆
  core:window:allow-set-size,         // 缩放
  core:event:allow-listen,            // 订阅 checkin-progress 等
  core:app:allow-version?             // 视需要
]
```

**关于点击穿透（进阶，MVP 不做）**：

- 若要做"矩形可点、外面穿透"，需要 `set-ignore-cursor-events`（`core:window:allow-set-ignore-cursor-events`）；
- 但它是**双刃剑**：默认全穿透后要**轮询全局光标位置**判断命中，再临时关闭穿透；
- **主要性能坑**：**绝不能每帧调 IPC**。建议 60~100ms 节流 + 仅在"命中矩形边缘附近"时才查询；
- **MVP 决定：不做**。窗口就是宠物包围盒（300×360），矩形可点可拖，最省事、最稳。

**权限标识符须先核对再写**（避免写错名导致启动即拒）：

```powershell
cargo tauri permission list      # 在 src-tauri/ 下，核对 allow-* 的准确拼写
```

## 6. 状态机与事件映射（核心）

### 6.1 状态定义

`src/pet/petState.ts` 定义宠物状态（**少而准**，避免状态爆炸）：

| 状态 | 语义 | 主素材 | 触发 |
|---|---|---|---|
| `idle` | 空闲（默认） | `待机呼吸休闲` | 启动 / 事件结束 / 静默 |
| `working` | 业务进行中 | `工作状态-忙碌点按` / `工作状态-思考冒泡` | 签到 start / 切换 start |
| `happy` | 成功 / 庆贺 | `工作状态-雀跃庆祝` | 签到 done 有成功项 |
| `sad` | 失败 / 出错 | `工作状态-垂头叹气冒汗` | done 有失败项 / 异常 |
| `rich` | 余额增长 | `余额-钱袋满溢` / `余额-数金皱眉` | 积分事件 |
| `broke` | 余额告急 | `余额-分文不剩` / `余额-袋空如洗` | 余额为 0 / 额度耗尽 |
| `sleepy` | 长时间无事件 | `原地小憩沉眠` / `哈欠连天` | 无事件 ≥ N 分钟 |
| `thinking` | P3 受控 | `深度思考碎碎念` | pet_say 流式期间 |

**状态迁移规则（关键，已对齐上游 `dsh_state.py` 的设计）**：

- **优先级聚合，而非简单抢占**。上游用固定优先级：`attention > error > working > thinking > idle`（多状态同时出现时取最高），**我们直接照搬这套思路**，映射为：

  ```
  需要你注意(attention) > 出错(sad) > 进行中(working) > 思考(thinking) > 空闲(idle)
  ```

  规则：**高优先级可以覆盖低优先级；低优先级不得打断高优先级**（避免"签到出错"被随后的"进度事件"冲掉）。
- `happy` / `rich` / `broke` 作为**瞬态提示**处理：播放一次后回落，**不参与优先级竞争**（它们不表达"需要关注"）。
- `sleepy` 由"最后事件时间戳"驱动（**定时器**，不靠事件），且**优先级低于所有业务态**。
- 同一优先级内，新事件覆盖旧事件，并 `clearTimeout` 旧的回落计时器。
- **气泡与动作状态解耦**（上游 `attention` 走"绕提示气泡"即可佐证）：状态决定动作，台词从对应池**随机取**，避免每次同一句。
- **只做状态标记，不改业务状态**（上游明确"不 `self.affect()`"）：宠物窗口**只读事件，绝不回写业务数据**。

const files = import.meta.glob<string>('../assets/pet/videos/*.webm', {

## 8. 素材工程与风险

### 8.1 体积与打包（首要现实问题）

- **已定：内置 31 个动作 = 13.0 MB**（业务相关全集，见 §6.3）。上游全量 106 个为 51.8 MB，多出的 38.7 MB 是节日彩蛋，**不内嵌**。
- **字体（4 MB）不引入**：授权未核实，P0 统一用系统字体。
- 目录：`src/assets/pet/videos/`（打包进 dist）。Vite 会把每个 webm 作为独立资源产出（>4 KB 不会被 base64 内联），文件名自动带 hash。
- 将来若要彩蛋动作，走 P4 的**素材包按需下载**，不要撑大安装包。

**Vite 注意**：默认 `assetsInlineLimit = 4096` 字节，webm（~500 KB）不会被内联为 base64，会作为独立资源产出——这是期望行为，**无需改配置**；但**不要**把 webm 放在会被内联的小文件规则下。

### 8.2 CSP（可能不需要改，但要验证）

现有 CSP（`tauri.conf.json` §security）：

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data: asset: http://asset.localhost; font-src 'self' data:;
connect-src 'self' ipc: http://ipc.localhost; object-src 'none'; base-uri 'self'; form-action 'self'
```

- **`media-src` 未声明 → 回退 `default-src 'self'`** → 同源 `<video src="/assets/xxx.webm">` **应当放行**，**无需改 CSP**。
- 但**必须实测**：WebView2 对 VP9 alpha 视频的加载与解码是否被 CSP / 解码器策略拦。若不通过，备选见 8.3。
- 只有"前端直连 7864 网关"时才需在 `connect-src` 放行（本方案**不采用**，见 §3 决策）。

### 8.3 渲染路线：`<video>` vs 帧序列（**已实测定案**）

**这是全案最大的技术不确定项，且有上游反证**：

- **反证**：`dsh-pet-indesktop` 已经有一整套素材，却**没有直接用播放器播 WebM**，而是自建帧序列供给链——
  `frameseq_provision.py`（136 KB，生成/下载/解码）+ `frameseq_clip.py`（47 KB，片段播放）+ `decode_fanout.py`（32 KB，多消费者解码分发）+ `frame_cache.py`（帧缓存）+ `predictive_prewarm.py`（前瞻预热）。
- **继续反证**：上游另有 `docs/ONE_DIR_PACKAGING.md` 提到 **"不预解码全部素材 = 更快启动"**，以及 **"窗口隐藏后暂停动画解码与活动定时器，隐藏时 CPU 占用 0"**，并另设 `first_frame_cache_max_mb`（默认 8 MB）做首帧缓存。
- **说明**：上游宁愿付出 200+ KB 代码代价也不用 `<video>`，**很可能是透明视频在"随机定位、逐帧控制、首帧预热、隐藏即停"这几件事上不可控**。

**因此不能默认 `<video>` 可行。P0 第一步就做最小验证 demo**，逐项测：

| 验证项 | 关注点 |
|---|---|
| 透明通道 | WebView2 内 `<video>` 播 VP9 alpha，**是否真渲染出透明像素**（社区反馈不一） |
| 首帧延迟 | 切动作时是否可见黑帧/白闪（对应上游的 `first_frame_cache`） |
| 逐帧控制 | 能否精确暂停在指定帧、能否指定播放段（对应上游 `frameseq_clip`） |
| 隐藏即停 | 窗口不可见时能否可靠停解码（对应上游 `memory_trim`） |
| 内存 | 多 action 预加载后的解码器内存占用 |

**降级决策树（依验证结果选一条）**：

1. 若 `<video>` 全部通过 → **首选**，零新增依赖，最省事。
2. 若透明 OK 但控制力不足（首帧闪、无法定格）→ **`<video>` 预加载池 + 双实例交替**，或少量动作改 **APNG / WebP 动图**（体积增大）。
3. 若透明失效或需要逐帧精确控制 → **转 PNG/WebP 序列帧 + `<canvas>` 播放**（对齐上游路线）。此路需素材转换（上游 `step04` 之后加一步），并要自己做帧缓存与预热，**工作量显著上升**。
4. 若都不行 → CSS 抖动 + 少量 PNG 帧的极简动画（最保守，只保留 idle/click）。

> 上游素材已是 640×360@24fps，**转帧序列的成本可控**；若走路线 3，直接复用上游 `scripts/convert_to_gif.py --force --clean` 的思路做批量转码。

#### 8.3.2 路线结论（**已定**）

> **走 `<video>` + WebM(VP9 alpha)，不采用上游的帧序列方案。**

依据：alpha 通道完整保留（T1）、首帧 3~51ms（T2）、窗口级透明确认生效、页面渲染正常。上游自建 200+ KB 帧序列链（`frameseq_provision` / `decode_fanout` / `frame_cache`）的复杂度，**在 WebView2 上不需要复制**——其动机更可能是 Qt 播放器侧的局限与"精确定格/片段裁剪"需求，而这两点在 P0 用不到。

**但必须配套三件事，否则会踩坑**：

1. **隐藏时必须主动停**（T4 结论）：WebView2 **不会**因为窗口隐藏而冻结 rAF/定时器。必须监听窗口可见性（前端 `visibilitychange` 或 Rust 侧通知）→ `video.pause()` + 取消 rAF。**否则隐藏后仍满速跑 144fps，纯烧 CPU/GPU。**
2. **处理 alpha 残留**：素材背景 alpha 集中在 1-50（约 8% 暗化），叠在浅色桌面上可能看到极淡的方形痕迹。两条路：
   - 素材侧用 ffmpeg 做 alpha 阈值清理（`alphaextract` + 阈值/`geq`），重新编码；
   - 或 P0 先接受（深色桌面几乎不可见），P1 再优化。
3. **不要依赖 rVFC 做定格校验**：暂停态 seek 后 rVFC 不回调。若将来需要"停在指定帧"，用像素哈希/像素比对验证，或对该功能改用帧序列。

**未验证项（不影响路线）**：解码器实际内存占用（需任务管理器读数）；`skipTaskbar` 在任务栏上的真实表现（`APPWINDOW` 位存在，需实测确认）。

**验证完成后的清理**（2026-10-19 执行结果）：**只删除验证期的冗余配置与启动器**——
`tauri.pet.conf.json`（pet 窗口已正式并入 `src-tauri/tauri.conf.json`）与 `scripts/pet-probe.mjs`（启动器已无用）。
**保留**：`src-tauri/capabilities/pet.json`、`src-tauri/src/commands/pet.rs`、`src/pet/`（含诊断页 `ProbeRoot.tsx` / `pet.css`）——
桌宠功能正式保留，`pet_probe_*` 诊断命令按原计划保留（对应 `?pet=1&probe=1` 页面）。

| 风险 | 说明 | 对策 |
|---|---|---|
| 新增依赖与红线冲突 | `AGENT.md` §13 明令"引入额外 UI 库 → 保持依赖最小" | 本方案**零新依赖**：不引 Live2D / Spine / 动画库 |

| 应用退出清理 | `RunEvent::Exit` 会停代理与 API 服务 | 宠物窗口**不持有**任何需清理的资源（纯前端），无额外清理 |

**四步在本仓库的对应与适配**

| 步骤 | 上游脚本 | 本地做法 | 备注 |
|---|---|---|---|
| 01 水印/通道填充 | `watermarm_step01.py` | 源素材带水印时先补纯绿底；自制素材可跳过 | 仅转载/换装素材需要 |

| 03 归一化 | `normalize_step03.py` | 统一 **2160×1215** 画布、站立居中、脚底对齐 | 关键常量 `FEET_Y=330` / `PAD=30`（**1215 画布口径**） |

**坐标换算（必须一致，否则角色会「飘」或「踩空」）**

- 归一化画布 `2160×1215` 与播放画布 `640×360` 同为 16:9，缩放比 = `640/2160 = 0.296296…`。
- 上游常量按 1215 画布口径：脚底线 `y=330` → 播放画布 `y≈97.8`；留白 `PAD=30` → `≈8.9`。
- 故**归一化阶段保持 2160×1215 不动**，仅在 step04 缩小；`PetSprite` 现有「视频贴底 + 按宽度铺满」的做法即可自然对齐（脚底贴窗口下沿）。

**产物校验（`check-asset.mjs` 必过，等价于现有 §8.3 的 T0b / T1 门槛）**

- 分辨率恰为 `640×360`、帧率 `24fps`、编码 `VP9 + Alpha`；
- 透明像素占比 **> 5%**（T1 门槛）；时长 > 0，`loop` 动作首尾帧可衔接；
- 脚底 / 水平居中位置与既有素材一致（按像素包围盒比对）；
- 任一不达标 → 直接失败退出，**禁止落盘**到 `videos/`。

**接线与合规**

- 落盘后同步 `src/assets/pet/manifest.json`：`id`（ASCII 别名）/ `中文原名` / `group` / `loop` / 画布规格；
- 新增 / 替换素材后：在 `THIRD_PARTY_NOTICES.md` 登记来源；来自上游则保留 MIT 头与 `LICENSE-dsh-pet.txt`；自制素材登记作者与许可；
- 换装 / 多形象：以「一套 `manifest.json` + `videos/` 目录」为一个**素材包单元**，即 P4 的 `pet_pack` 机制（内置包 = 当前 `src/assets/pet`）。

**分期**

1. 先做 `check-asset.mjs`（校验器）——用现有 31 个 WebM 当基线，成本最低、收益最直接；
2. 再 vendor 上游 4 步脚本 + `build-asset.mjs` 串联（依赖便携 ffmpeg / libvpx）；

## 12. 红线对齐（本方案不做什么）

- ❌ 不引入 React Router / Redux / 任何 UI 库 / Live2D / Spine（`AGENT.md` §13）
- ❌ 不改 Rust 命令**嵌套参数**字段名（`CheckinOpts` 等）——本方案只**读**事件，不改契约
- ❌ 不把顶层参数改 camelCase
- ❌ 不用 `window.confirm()`（用现有自定义 `Modal`）
- ❌ 不用 `api.prevent_close()`（会触发 Chromium 1412 错误）
- ❌ 不新增第二个 Vite 构建入口（复用 `index.html` 分流）
- ❌ **不引入上游的"看屏幕"截图功能**——上游把它截图后**直接发送给模型服务商**，与本项目"零外发"红线**直接冲突**
- ❌ 不引入上游的音乐/歌词/占卜/节日/图鉴等外围模块（工作量膨胀且非目标）
- ❌ 宠物侧**不另存 API Key**（复用现有网关即可），也不写任何业务数据
- ❌ 不新增任何网络外发（"零外发"红线；P3 仅走本机 `127.0.0.1` 网关）
