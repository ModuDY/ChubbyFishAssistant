## 0. 一句话结论

现状的三个模块（桌宠 / 网关 / 壁纸）都是**"把已有能力做得更好看"**，不是"把每天要干的事干得更快"。
所以改造的关键不在于再加一个仪表盘，而在于补上**「今天该做什么」的入口（工作台）**、**「重复动作自动化」的手（工作流）**、**「查过就忘的东西」的记忆（知识库）**，并且让这三层复用已有的账号池、调度器、事件总线——**不新建后端、不新起 HTTP、不引入重依赖**。

## 2. 现状诊断：为什么"帮助太少"

| 现状 | 问题 |
|---|---|
| 首页 `Dashboard` = 账号数 / 积分 / 签到趋势 / 积分榜 | 这是**运维视图**（池子健康度），不是**工作视图**（今天我该干什么）。每天打开看到的是"机器状态"，不是"我的待办" |
| 14 个定时任务写死在 `tasks/scheduler.rs::TASKS` | 流程是**代码**，不是**数据**。想改"先签到再切号再通知"必须改 Rust 并重新编译（新增任务要动 4 处：`TASKS` / `enabled()` / `effective_hhmm()` / `run_task()`） |
| 40+ 个 Tauri 命令 + 大量业务事件 | 能力**齐全但离散**，用户必须记住"哪个页面的哪个按钮"；跨模块串联（签到→切换→通知→AI 总结）完全靠人 |
| `docs/`、`CHANGELOG.md`、会话导出、API 日志 | 全是**已经在自己机器上、且反复查阅**的高价值语料，但只能靠 Ctrl+F |
| 桌宠 / 壁纸 / 网关 | 已把"状态可见性"和"娱乐性"做到位了，边际收益递减 |

**结论**：缺的不是功能，是**"把已有能力串成一天的工作流"的那一层**。

```
        │ (声明式 step)  │检索 │ (FTS5 + 引用)   │
        └───────┬────────┘     └───────┬─────────┘
                │ 复用                  │ 复用
     ┌──────────▼──────────┐  ┌────────▼─────────┐
     │ tasks/scheduler.rs  │  │ api_server       │
     │ (退避/冷却/状态)     │  │ run_chat_completion│
     └─────────────────────┘  └──────────────────┘
                │ 事件
        ┌───────▼──────────────────────────┐
        │ 既有事件总线 + 桌宠 PetSignal 状态机 │
        └──────────────────────────────────┘
                │ 对外
        ┌───────▼──────────┐
        │ MCP stdio server │──▶ Claude Code / Cursor / Trae
        └──────────────────┘
```

**三条贯穿性红线**（与 `AGENT.md` §12/§13 一致）：
1. **零外发**：知识库 embedding 不接云端（见 §5.3 的取舍），MCP 只走 stdio；
2. **零新增重依赖**：不引 React Router / 组件库 / 向量库 / 脚本引擎；
3. **数据可弃**：知识库索引是**派生数据**（学 siyuan），删除可重建，用户内容不依赖索引。

## 4. 工作台（P0，先做，1~2 天）

### 4.1 定位（唯一要记住的一句）

> **不是"又一个 dashboard"，是"今天这一屏"：只读聚合 + 一键执行 + 三秒捕获。**

### 4.2 信息架构（5 个区块，按"每天真实会看"排序）

| 区块 | 内容 | 数据来源（全部已有） | 交互 |
|---|---|---|---|
| **① 今日状态条** | 今日已签 N/M、网关状态、未处理告警数（JWT 24h / 积分 7 天）、今日 token 消耗 | `accounts` / `apiStatus` / `accounts[].jwt_exp_hours` / `api_usage` | 点击跳详情 |
| **② 待办 / 提醒**（核心） | 每条 = 一句话 + 一个动作按钮。例："3 个账号 JWT 24h 内过期 → 一键续期"、"Buddy 池今日未签 → 去签到"、"知识库 2 天未索引 → 立即索引" | 由**规则表**生成，不是手写待办 | 直接执行（调既有命令） |
| **③ 一键动作** | 签到全部 / 切换上次账号 / 打开网关 / 复制 API Base / 新建笔记 / 问知识库 | 既有 `api.*` | 单击执行 + toast |
| **④ 最近 & 常用** | 最近打开的知识库文档 / 最近 5 条工作流运行结果 / 常用流程一键跑 | 新增（KB `最近`、`workflow_runs`） | 打开 |
| **⑤ 快速捕获** | 一个输入框：输入文字 → 存为知识库笔记；输入 `/` 走命令；输入 `?` 走知识库问答 | 新增 | Enter 提交 |

> **为什么没有"任务管理"**：Task 实体会把产品拖进"待办 App"赛道（录入负担，见 §1.1 批评）。待办区块由**规则 + 已有数据**自动生成，用户不需要维护。

### 4.3 技术方案

| 项 | 决定 | 理由 |
|---|---|---|
| widget 机制 | **注册表 + 布局持久化 JSON**，不做 YAML 文件 | 单人自用；注册表 = `src/pages/workbench/widgets/index.ts` 导出 `{ key, title, span, Component }`，布局存 kv `workbench_layout`（`{ widgets: [{key, span, hidden}] }`） |
| 数据获取 | **前端直调既有 `api.*`，不新增后端命令**（除布局读写） | 零后端成本；P0 阶段后端只加 `workbench_layout_get/set` 或直接复用 `settings_get/set` |
| 位置 | **跨应用固定入口**，不塞进某个应用的 NAV | 现有 `Sidebar` 按 `activeApp` 切菜单，工作台属于系统级；塞进 Trae 菜单会在切到 Buddy 时消失 |
| 默认首屏 | 新增 `settings.default_view`（缺省 `workbench`） | 不动 `APP_HOME_VIEW`（那是"切应用落地页"语义，改动面大） |
| 样式 | 只用 `index.css` 的 `.card` / `.btn-*` / `.chip` + slate/zinc 系 class | 保证跟随 6 套主题（`--c-slate-*` 变量） |

## 5. 知识库（P1，2.5~3.5 天）

### 5.1 定位（2026-10-22 重大调整）

> **改口径**：从"本地建索引 → 本地检索 → 只把片段喂给 AI"改为 **"本地只存文件，检索与作答交给 AI"**，同时**保留本地 FTS5 作为兜底与预筛**。
> 不保留向量检索（原因见 §5.3）。

三层分工：

| 层 | 职责 | 位置 |
|---|---|---|
| 存储层 | 原始文件 + 文件清单元数据 | 磁盘 + `kb_docs` |
| 兜底层 | 关键词检索（网关不可用时的**唯一**可用路径）+ Stage 1 预筛 | 本地 FTS5 |
| 智能层 | 选文件 → 读正文 → 作答 → 带引用 | 网关 → 上游 AI |

**为什么这个分工比原方案好**：

1. **中文分词从"必须解决的核心问题"降级为"兜底路径的实现细节"。** AI 不需要分词就能理解中文——这正是原方案最脏的一块（trigram 兼容性、bigram 预分词、2 字查询回落 `LIKE`）。
2. **chunk 切分策略不需要调参。** AI 直接读大段/全文，"按消息边界还是定长"这类反复调参的活消失了。
3. **索引陈旧不再影响回答质量。** AI 读的是磁盘上的**当前**内容；索引只在兜底模式才可能读到旧数据。

**代价（已与用户确认，明确接受）**：

| 代价 | 性质 | 缓解 |
|---|---|---|
| **本地文档正文会发往上游 AI**，含会话正文 | 内容外发范围扩大（原方案只外发 prompt）。`AGENT.md` §12 "零外发"指不连自有后端，网关访问上游本就存在，故不破红线，但**外发内容性质变了** | 用户确认接受；靠 §5.6 外发审计让每次外发都可回查 |
| 每次提问 ≥ 2 次模型调用，同一问题问两遍不省 | 成本线性增长 | 用户确认不设成本上限 |
| AI 给出的**行号是生成的**，可能编造 | 引用可信度 | 强制事后校验（§5.3 第四步），校验不过就降级只给文件 |

### 5.2 索引什么（四个来源，全部"已在本机且会反复查"）

> **决策（2026-10-22，用户确认）：四类来源全部纳入 P1**，第四类会话正文不推迟。

| 来源 | 现状 | 价值 |
|---|---|---|
| 项目 `docs/` + `CHANGELOG.md` | 已有 33 个 md | 查自己的设计决策与红线的**最高频场景** |
| 用户指定目录（笔记 / 收藏 / 下载） | 用户手动加 | 通用 |
| 网关请求日志 + `data/exports/` | 已有 `api_logs_*`、导出产物 | "上次那个报错是怎么回事" |
| **Trae / Buddy / Qoder 会话正文** | 解析器已存在：`workbuddy_stats.rs` 已有三路扫描（`~/.workbuddy` / `~/.codebuddy` / `CodeBuddy IDE history/*/index.json`）+ `mtime+size` 增量缓存 + 跨文件 request id 去重 | "上周让我改的那段代码思路" |

> 后两类是**别人没有的数据源**，也是这个知识库相对 AnythingLLM 的唯一差异点。

#### 5.2.1 会话正文口径（AI 检索模式下的精简版）

原方案为"先进索引库"设计了复杂的收敛口径（chunk 元数据、单条上限、默认不搜……）。改为 AI 检索后，这些**大部分不再必要**——因为 AI 读的是文件本身，不需要预切分。保留的部分：

| 项 | 决定 | 理由 |
|---|---|---|
| 定位入口 | **复用 `commands/workbuddy_stats.rs` 的文件定位与缓存层**，只取「文件路径 + mtime + size 清单」，不重写扫描器 | 该扫描器已踩完坑（结构定向、`DirEntry::file_type()`、跳过 `messages/file-tree`、跨 uid 重复去重），重写必定复现同样问题 |
| 读取内容 | **只取 user 消息 + assistant 正文文本**；`tool_use` / `tool_result` 参数、`file-tree`、`check-point`、`subagents/` 一律**不读取** | 工具参数体积占比高、语义噪音大，且常含大段代码/路径。这是**成本控制**而非索引优化 |
| 单文件上限 | 单会话正文截断到 **200 KB**，超出在 prompt 里明示 `[已截断]` | 防个别超长会话挤爆单次上下文（用户不设 token 上限，但**单文件上限不等于全局预算**，仍需截断保护） |
| 外发 | **默认全发**（用户 2026-10-22 明确确认：含会话正文全文） | 知情接受；靠 §5.6 外发审计可回查每次发了什么 |
| MCP 出口 | 走 MCP 暴露时，会话类结果**默认不返回**，需 `include_chats: true` | MCP 调用方是外部进程，与"用户本人在自己应用里操作"风险不同，仍保留最小暴露原则 |
| 去重 | 会话文件跨 uid 整份重复时**整文件跳过**（复用现有 id 集合缓存策略） | 已实测本机有 609/4123 行重复 |


### 5.3 检索与作答流程（AI 主路 + FTS5 兜底）

#### 5.3.1 主路径：两步 AI 检索

```
用户提问
  ↓
【0】本地预筛（必做，尤其会话源）
     - docs/笔记源：文件数少（33 个 md），清单直接全量进入 Stage 1
     - 会话源：4000+ 行 / 数百文件，先按「时间窗 + 关键词命中」本地筛到 ≤50 个，
       否则清单本身就塞不进上下文
  ↓
【1】Stage 1 · 选文件（便宜档模型）
     输入：候选文件清单（path / title / mtime / 首行摘要）
     输出：≤5 个候选文件路径 + 一句话理由
     实现：优先 function calling（见 §5.3.3 待验证）；不支持则输出 JSON 文本后解析
  ↓
【2】Stage 2 · 读正文并作答（主力档模型）
     输入：选中文件正文（受单文件 200 KB 截断保护）
     输出：答案 + 行内引用 [N]，每条引用解析为 {path, start_line, end_line}
  ↓
【3】引用校验（必做，不可跳过）
     - 路径真实存在？
     - 起止行 ≤ 该文件实际行数？
     - 校验通过 → 引用可点击跳转
     - 校验失败 → **降级为只给文件链接、不给行号**，并在 UI 标注「行号未能校验」
  ↓
渲染（流式）
```

#### 5.3.2 兜底路径：本地 FTS5

**触发条件**：网关未启动 / 额度耗尽 / 上游报错 / 用户显式选"仅本地搜索"。

| 项 | 决定 | 依据 |
|---|---|---|
| 引擎 | **SQLite FTS5**，零新增依赖 | 已实测 `findstr fts5 sqlite3.lib` → `FTS5_PRESENT`（`rusqlite 0.32 bundled`） |
| 中文分词 | 主选 `tokenize='trigram'`；2 字及以下查询回落 `LIKE`；若该版本 trigram 不可用则改**写入期 bigram 预分词** | **实现第一步必须先跑 `SELECT sqlite_version()` + 建表试跑确认**（这是原方案遗留的唯一硬验证项） |
| 检索范围 | 只返回**文件级**命中（path + 命中行号区间），不返回 chunk 语义段落 | 兜底模式不需要拼 prompt，只需"能在原文里定位到" |
| 与主路径关系 | Stage 1 **复用**同一份 FTS5 索引做预筛；兜底模式直接复用其结果 | 一套索引两用，不重复建设 |

#### 5.3.3 三个待验证项（开工前 30 分钟内跑完）

| # | 待验证 | 影响 | 验证方式 |
|---|---|---|---|
| ① | 上游是否支持 **function calling**（`tools` / `tool_choice`） | 决定 Stage 1 用 tool call 还是 JSON 文本解析 | 网关代码里 `tools` **0 处命中**，说明是原样透传、从未验证过；直接构造一次带 tools 的请求打上游 |
| ② | 当前 SQLite 版本 **trigram 分词器是否可用** | 决定中文分词走 trigram 还是 bigram 预分词 | `SELECT sqlite_version()` + 建 FTS5 表试跑 |
| ③ | 单次 Stage 2 实际能稳定吃下多大上下文 | 决定会话源预筛窗口（≤50 还是更小） | 用最长会话实测，观察是否截断/报错 |

**①② 未通过都有 Plan B**：① 失败 → JSON 文本输出 + 容错解析（多一层解析，不影响功能）；② 失败 → bigram 预分词（约 20 行，写入与查询同口径处理）。

#### 5.3.4 不做向量检索（原因不变，且更充分了）

| 原因 | 说明 |
|---|---|
| 网关**没有 embeddings 端点** | `routes.rs:1116` 明确 `/v1/embeddings` 返回 **501**（"上游服务无 embeddings 能力"）。要做向量只能外发到第三方或内置 ONNX，前者破红线、后者重依赖 |
| sqlite-vec 仍是 pre-v1 | 官方明示会有 breaking changes |
| **AI 检索已覆盖向量要解决的场景** | 向量的价值是"语义相似但用词不同"。Stage 1 让 AI 读标题+摘要选文件，本身就能跨过措辞差异——用 AI 替代 embedding，是这次的**主要收益来源** |

#### 5.3.5 引用红线

每条 AI 回答必须带 `[N]` 行内引用，且**经过 §5.3.1 第三步校验**才可点击跳转。校验不过就降级标注。

> 没有可信引用的知识库不可信；而 AI 生成的行号**天然不可信**，所以校验不是可选项。

### 5.4 数据模型（全部进 `aiwork.sqlite`，比原方案少一张表）

```
kb_sources    (行表，进 ROW_TABLES)  pk=source_id  → {kind, root, enabled, last_scan_ms, doc_count}
kb_docs       (行表，进 ROW_TABLES)  pk=doc_id     → {source_id, path, title, mtime, size, hash, status, truncated}
kb_fts        (FTS5 虚拟表)                        → 兜底检索 + Stage 1 预筛（可弃可重建）
kb_notes      (行表，进 ROW_TABLES)  pk=note_id   → 快速捕获的短笔记
```

**变更点**：

- **删掉 `kb_chunks`**。原方案要存 chunk 正文供拼 prompt，现在 AI 直接读原文件，chunk 表没有存在意义。这是这次改口径**省下最多工作量**的一项。
- `kb_docs` 加 `truncated`：标记"该文件超过 200 KB 被截断"，让 UI 如实提示，避免 AI 以为看到了全文。
- `kb_fts` 存**行级**条目（`doc_id, line_no, text`）而非 chunk 级，兜底检索直接返回"哪几行命中"，跳转语义更直接。
- **索引可弃**：删掉 `kb_fts` 后全量重建，`kb_docs` 只留元数据（学 siyuan 的内容/索引分离）。
- 增量判定：`mtime + size` 相同则跳过；不同则重算 `hash`（`sha2` 已有）。
- 新增表**不必 bump `SCHEMA_VERSION`**（`schema::init` 每次开库都跑 `CREATE TABLE IF NOT EXISTS`，见 `store/schema.rs:274`）；但**必须登记 `ROW_TABLES`**（`schema.rs:15`），否则 `rows_all/row_upsert` 报"非法表名"。

### 5.5 接口

| 命令 | 说明 |
|---|---|
| `kb_source_list` / `kb_source_add(root, kind)` / `kb_source_remove(id)` | 索引源管理 |
| `kb_scan_run(source_id?, full?)` | 只扫**文件清单**（path/mtime/size/title），**不解析正文**，极快；NDJSON 事件 `kb-scan-progress` |
| `kb_index_run(source_id?)` | 建 FTS5 行级索引（兜底 + 预筛用）；NDJSON 事件 `kb-index-progress` |
| `kb_search(query, opts)` → `KbHit[]` | **本地 FTS5 检索**（兜底路径）。opts：`limit / source_ids / chats_only` |
| `kb_ask(query, opts?)` → 流式 | **主路径**：预筛 → Stage 1 选文件 → Stage 2 作答 → 引用校验。事件 `kb-ask-stage{stage}` 让 UI 显示"正在选文件/正在阅读/正在作答" |
| `kb_doc_get(doc_id, from_line?, lines?)` | 读原文片段（复用既有 `read_text_file` 白名单约束） |
| `kb_recent()` | 工作台区块④数据源 |

**性能红线**（本项目已有教训，见 AGENT.md §5 的 `profile_list` / `proxy_logs_list` / `workbuddy_token_stats`）：

- 扫描与建索引必须 `spawn_blocking` + `#[tauri::command(async)]`；
- 前端 `INVOKE_TIMEOUT_OVERRIDES`（`src/lib/tauri.ts:110`）**必须登记** `kb_scan_run` / `kb_index_run` / `kb_ask`（默认 120s 会超时，`kb_ask` 两次模型调用尤其容易超）；
- 扫描走 `DirEntry::file_type()` 免额外 stat，跳过 `node_modules / target / .git`。

**内部调用口径**：`kb_ask` 的两次模型调用走**进程内** `routes::run_chat_completion(state, key, body, proto)`（`api_server/routes.rs:508`），**不走 HTTP 回环**——网关路由全经 `bearer_auth`，回环需 API Key 且污染 Key 用量。key 记 `internal:kb`，可单独审计。这与桌宠 `pet_say` 是同一套路（AGENT.md §5 已验证）。

### 5.6 外发审计（新增，因"默认全发"而必须）

用户确认"会话正文默认全发"，则**每次外发都必须可回查**，否则出了问题无法定位是哪次问答把哪份文件发了出去。

- 每次 `kb_ask` 落 `kb_ask_log` 行表：`{ts, query, stage1_sent[{doc_id,path,bytes}], stage2_sent[{doc_id,path,bytes,truncated}], answer_chars, citations_valid, err}`；
- **只记文件路径与字节数，不记正文**（避免审计表本身变成第二份敏感数据）；
- 设置页提供"查看最近外发记录"，按来源类型分组统计（docs / 笔记 / 日志 / 会话）；
- 首次使用 `kb_ask` 且**包含会话类文件**时，弹一次明确提示（"本次会将会话正文发送至上游 AI"），确认后不再重复（落 kv）。

### 5.7 验收

**主路径**

- 问"上次那个 501 报错是怎么回事"能从 `docs/` 与导出日志里找到并作答；
- 每次回答的引用都经过校验：**故意构造一个假行号，验证降级路径生效**（不给行号、标注未校验）；
- 网关未启动时 `kb_ask` **明确报错并引导**，不是静默失败或空回答。

**兜底路径**

- `kb_search` 在网关**完全关闭**时仍可用；
- 中文 2 字 / 3 字 / 长句三种查询都有合理结果；
- 删除 `kb_fts` 后重建，结果一致（证明索引可弃）。

**成本可观测**

- `kb_ask_log` 能回答"这次问答发了哪些文件、共多少字节"。这是"不设预算"的前提——**不设上限不等于不可观测**；

## 6. 工作流（P2，5~7 天）

### 6.1 定位（最重要的取舍）

> **不做可视化画布。** 用 **JSON/YAML 声明式 step 列表 + 极简变量引用**，把现有 14 个写死的定时任务升级为可配置数据。

理由：n8n / Activepieces 的画布价值在**多租户、非开发者自建**；本项目是单人自用、作者就是开发者，**画布的编辑成本远高于手写 10 行 JSON**，而维护一张画布（拖拽、连线、坐标、撤销）是数千行前端的无底洞。

### 6.2 定义格式

```json
{
  "id": "wf-morning",
  "name": "早间例行",
  "enabled": true,
  "version": 1,
  "trigger": { "type": "schedule", "mode": "daily", "hhmm": "09:00" },
  "steps": [
    { "id": "s1", "type": "checkin",  "with": { "scope": "all" } },
    { "id": "s2", "type": "kb_index", "with": { "full": false }, "when": "{{s1.ok}} > 0" },
    { "id": "s3", "type": "notify",   "with": { "title": "早间例行完成", "body": "签到 {{s1.ok}} 成功 / {{s1.failed}} 失败" } }
  ]
}
```

**step 类型白名单（P2 首批 8 个，全部是"已有命令的编排"，不新增能力）**：

| type | 复用 | 说明 |
|---|---|---|
| `checkin` / `switch_account` / `profile_backup` | 既有 `tasks::*` / `switcher::run_action` | 直接调已有业务函数 |
| `http` | `ureq`（已有） | 仅 GET/POST，域名白名单 + 不发凭证（防变成数据外发通道） |
| `kb_search` / `ai_chat` | 本方案 §5、`run_chat_completion` | 串联知识库与账号池 |
| `notify` | `push_notify` / `NotifyEvent` | 系统通知 |
| `wait` / `condition` | — | 延时 / 极简条件 |

**变量引用**：仅 `{{stepId.path}}`（只读前置步骤的输出 JSON 路径）+ 条件 `{{a.b}} op value`，`op ∈ > < == != contains`。
**明确不做表达式求值引擎**（不引 rhai / boa / eval）——这是防"工作流变成脚本语言"的关键闸门。

### 6.3 执行与状态

- **执行语义**：串行 DAG，步骤失败默认**终止并标记**（不做花式 continue-on-error，P2 只支持 `onError: "stop" | "continue"`）；
- **步骤级重试**：`retry: { times, backoffMs }`（学 activepieces 的步骤级重试，非整体重试）；
- **状态落库**：新增行表 `workflow_runs`（`pk=run_id` → `{workflow_id, version, status, started_ms, ended_ms, steps:[{id,status,output,error,ms}]}`）——学 windmill"状态全在 DB"；
- **僵尸检测**：单次运行超过 `workflow_run_timeout_secs`（默认 600）标记 `timeout`，**不自动重跑**（重跑可能重复签到/重复扣积分——比 windmill 保守，因为我们的步骤有副作用）；
- **并发**：同一 `workflow_id` 同时只跑一份（复用 `skipped_busy` 语义，学 Qoder 的跨进程锁）；
- **版本化**：`kb`/`workflow` 定义变更时 bump `version`，`workflow_runs` 记录当时的 `version`，历史可解释。

### 6.4 与现有调度器的关系（不做两套调度）

- **不新建调度器**。`tasks/scheduler.rs` 已有：60s tick、启动 90s 后首跑、指数退避（30→60→120min）、`skipped_busy` 幂等跳过、状态落 kv、失败通知。这些都直接复用。
- 做法：`TASKS` 中新增**一个** `kind: "workflow"` 的调度项，`sched_plan` 里按 `workflow_defs` 里各定义的 `trigger.mode/hhmm` 展开判定；`run_task` 分支按 key 找到定义并交给 `workflow::engine::run`。
- → **净效果**：原来"新增一个定时动作要改 4 处 Rust 并重编译"，变成"在 JSON 里加一条 step"。
- 同时保留 `--task-run wf-<id>` 走 `tasks/mod.rs::run_cli_task`，供 schtasks 用。

### 6.5 接口

`workflow_list` / `workflow_get(id)` / `workflow_save(def)` / `workflow_delete(id)` / `workflow_run(id, dry?)` / `workflow_run_list(limit)` / `workflow_run_get(run_id)` / `workflow_validate(def)`
事件：`workflow-progress`（`{runId, stepId, status, ms}`，对齐 `checkin-progress`）、`workflow-done`。

### 6.6 验收

- 用 JSON 复刻现有"早间例行"（签到 → 条件 → 通知），行为与今天的硬编码任务一致；
- 中途 kill 进程，重启后 `workflow_run_list` 能看到那条 `aborted` 记录，不会重复执行；
- `workflow_validate` 能拦住：循环引用、未知 step type、引用不存在的 stepId、`http` 域名不在白名单；
- 同一流程连点两次只跑一份。

## 7. MCP 出口（P3，2~3 天）——杠杆最高的一件事

**为什么单列**：前三个模块的价值都还在"打开我们的应用"这个前提下；MCP 让它变成 **"你正在 Claude Code / Cursor / Trae 里干活时，可以直接调我们的知识库和工作流"**——一次投入，所有 AI 工具都能用。

> **决策（2026-10-22，用户确认）：写操作开放**，不做"只读沙箱"。理由：MCP 的全部价值在于"让 Claude Code 帮我跑早间例行"，只读等于把最有用的部分阉掉。

- 形态：**stdio MCP server**（子进程，零网络、零端口、零鉴权），主 exe 增加 `--mcp-server` 启动模式（对齐既有 `--task-run` CLI 模式）；
- 首批工具：`kb_search`（带引用）、`kb_doc_get`、`workflow_list`、`workflow_run`、`account_status`（只读池健康度）、`gateway_models`；
- 复用 §5 / §6 的 Rust 函数，**不新增 HTTP 端点**（`aiwork-server` docker 分支将来可另行暴露）。
- 依据：`hypothesi/mcp-server-tauri`、`delorenj/tauri-plugin-mcp` 已验证 Tauri + stdio MCP 组合可行。

### 7.1 写操作开放后的四道闸门（必须同时落地，否则不开）

开放写权限等于**给外部进程一个能签到、切号、扣积分的入口**，因此不能只靠"命名显式"：

| 闸门 | 内容 | 落点 |
|---|---|---|
| **① 工具分级** | `read`（`kb_search`/`kb_doc_get`/`workflow_list`/`account_status`/`gateway_models`）默认开；`write`（`workflow_run`/`kb_index_run`/`switch_account`）默认**关**，需在系统设置页显式勾选并二次确认后写入 kv `mcp_allow_write` | 设置页 + `--mcp-server` 启动时读取 |
| **② 干跑前置** | 每个 write 工具都接受 `dry: true`，返回"将会执行什么"而不执行；MCP tool description 里明示"不确定时先 dry" | 引擎侧统一拦截 |
| **③ 幂等 + 限流** | 同一 `workflow_id` 互斥（已有语义）；**每 60s 全局 write 次数上限**（默认 3），超限返回明确错误而非排队 | `mcp/guard.rs` |
| **④ 审计** | 每次 write 落 `mcp_audit` 行表：`{ts, tool, args摘要, caller_pid, caller_exe, result}`，MCP 侧无法关闭 | 与工作台"最近运行"共用展示 |

> 附加约束：`switch_account` 等**改变用户当前环境**的操作不开放给 MCP（会把人正在用的 IDE 账号换掉）；MCP 只开放"跑工作流 / 建索引 / 查询"三类。

## 8. 明确不做（防膨胀，与 §四"已排除项"同性质）

| 不做 | 原因 |
|---|---|
| 可视化流程画布（拖拽连线） | 单人自用的编辑成本远高于 JSON；维护代价数千行前端 |
| 完整 Task / 项目 / 子任务实体 + 时间追踪 | 会把产品拖成待办 App，且引入录入负担（DailyHub 被批评的通病） |
| 任意代码执行（node/python 子进程沙箱） | 安全面与打包体积双输；白名单 step 已覆盖真实需求 |
| 向量库（sqlite-vec / LanceDB） | gateway 无 embeddings 端点，外发破红线；本地模型太重；pre-v1 不稳定 |
| 云端 embedding / 云端同步 | 零外发红线 |
| 全盘文件索引 | 索引代价与噪音比收益高；改为显式目录白名单 |
| 多用户 / RBAC / 分享链接 | 单人自用 |
| 引入 React Router / 组件库 | `AGENT.md` §13 红线 |

## 9. 分期计划

| 期 | 内容 | 预估 | 依赖 | 可独立交付 |
|---|---|---|---|---|
| **P0** | 工作台（5 区块 + widget 注册表 + 默认首屏） | 1~2 天 | 无（纯前端 + kv 布局） | 是 |
| **P1** | 知识库（扫描清单 + FTS5 兜底 + **两步 AI 检索** + 引用校验 + 外发审计） | 2.5~3.5 天 | 无 | 是 |
| **P2** | 工作流（定义/校验/引擎/运行表 + 调度器 `kind:"workflow"`） | 5~7 天 | 建议在 P1 后（`kb_search` step 才有意义） | 是 |
| **P3** | MCP stdio + `kb_ask` 接工作台/桌宠 | 2~3 天 | P1 | 是 |

**建议顺序**：`P0 → P1 → P3 → P2`。
理由：P0 一周内就能改变日常体验（先拿到正反馈）；P1+P3 打开"知识库被外部 AI 工具调用"的复利；P2 最重且最容易做偏，放到最后、并且届时用真实需求反向裁剪 step 白名单。

### 首次开工前必做的事（`AGENT.md` §16 红线）
1. `git fetch --all --tags --prune` + `git pull`；
2. 本方案落地时**同步更新 `AGENT.md`** 的目录地图 / 命令契约 / 事件表 / 数据文件说明；
3. 新增待办项登记进 `docs/backlog.md`（唯一待办依据），本文件只留方案。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 工作台变成"又一个没人看的仪表盘" | 区块②的规则必须**只列"今天确实要动手"的事**（JWT 临期、今日未签、扫描清单陈旧），数量少而准；没内容时整块隐藏而不是显示空卡 |
| 知识库扫描慢 / 卡 UI | `spawn_blocking` + `async` 命令 + `INVOKE_TIMEOUT_OVERRIDES` + 增量 mtime 判定；扫描跳过 `target/node_modules` |
| **AI 引用行号造假** | 强制 §5.3.1 第三步校验；校验不过降级"只给文件不给行号"并在 UI 标注（这是本方案**最容易被跳过的一步**） |
| **外发内容不可回查** | §5.6 `kb_ask_log`：每次记"哪些文件、多少字节"，只记路径不记正文；首次含会话外发弹一次确认 |
| **AI 检索回答不了"本地精确匹配"类问题**（查某个固定字符串/编号） | FTS5 兜底路径始终可用，且 UI 明确提示"仅本地搜索"可绕过 AI |
| **网关不可用时主路径整体失效** | 兜底路径独立可用（这是保留 FTS5 的核心原因，不是可选优化） |
| FTS5 中文效果不达标 | 先实测 trigram；不达标退 bigram 预分词。**注意：这只影响兜底路径质量，不影响主路径**——AI 检索不依赖分词 |
| 会话源候选文件过多导致 Stage 1 超上下文 | 本地预筛（时间窗 + 关键词）压到 ≤50 个再进 Stage 1；实测确认后再调阈值 |
| 工作流重复执行造成副作用（重复签到/重复扣积分） | 同 flow 互斥 + 超时只标记不重跑 + `dry` 模式 + 运行记录可审计 |
| 页面数量继续膨胀、侧栏塞满 | 工作台是**入口而非并列页**；知识库/工作流各只加 1 页，其余能力以 widget 形态进工作台 |
| 改动面过大导致回归 | 每期独立可交付、独立 `npm run typecheck` + `npm test`；不动既有 `Dashboard` 与 14 个定时任务的既有行为（新流程与原流程并存，验证后再迁） |
