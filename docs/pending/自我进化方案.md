# 网关「自我进化」方案（待实现）

> 状态：方案 / 未开工（2026-10-19）
> 参考：`Ebony-Vinyl/dsh-our-free-model`（下称 OFM）
> 关联：`AGENT.md` §5（网关调度）、`docs/pending/桌宠结合设计方案.md`

## 1. 先澄清"自我进化"是什么

不是让 AI 改自己的代码，而是让**网关的策略参数**具备闭环：

```
观测（真实请求结果） → 决策（规则算出建议值） → 执行（带护栏热应用）
      ↑                                                    ↓
      └──────────── 评估（效果对比，劣化自动回滚） ←────────┘
                              ↓
                    固化（写入 kv，下次启动沿用）
```

一句话：**用真实数据把"调参"从手工变成自动，并且可回滚。**

## 2. OFM 有什么、我们缺什么

| OFM 机制 | 我们现状 | 差距 |
|---|---|---|
| `probes/availability-matrix` 主动探测端点/模型可用性 | 只有**被动**失败计数 + 冷却（请求失败才知道） | 缺主动探测；缺"能力维度"（tool calling / reasoning / 长上下文 / 图像） |
| `local-optimize` 请求短路（5 类可本地作答的请求） | 无 | 可加：客户端的心跳/quota/标题类请求直接本地回，省额度与延迟 |
| `speed-stat` / `heatmap` | 有用量统计（请求数/token/耗时按日） | 缺**分钟级**滚动统计（成功率、P50/P95 延迟），无法支撑实时决策 |
| `picks` / `combo-advance` | 有 `weighted_score` 选号 + 池内降级 | 缺"跨池接力"（主池失败自动换池并继承上下文） |
| `retry-safety` / `recovery` | 有冷却、自动解冻 | 缺进程级自愈（连接池重建、服务重启） |
| `feed/` + `integrity` + `provenance` | 无 | 远端规则下发 + 签名校验，**风险高，建议最后做** |

## 3. 我们做哪几层（按性价比排序）

### L1 自观测（地基，必须先做）

**目标**：每个上游/账号都有分钟级健康画像。

数据结构（内存 + 定期落盘 `kv: evolution_metrics`）：

```text
MetricKey = { app: "trae"|"wb"|"qoder"|"doubao", uid | "-" }
Metric = {
  window_5m:  { ok, fail, timeout, p50_ms, p95_ms },
  window_1h:  { ok, fail, p50_ms, p95_ms },
  last_error: { type, at },
  ewma_success: f32,   // 0..1，半衰期 5 分钟
  ewma_latency: f32,   // ms
}
```

写入点：`api_server` 的 dispatch 出口（成功/失败/超时各记一次）——**不新增请求**，纯观测。

### L2 自调参（核心价值）

只允许动 **4 个参数**，每个都有硬边界与冷却期：

| 参数 | 现状 | 自适应规则（示例） | 边界 |
|---|---|---|---|
| `hedge_threshold_ms` | 静态设置 | 池内 P95 延迟连升 3 个窗口 → 下调 20%（更早并行请求） | 200 ~ 3000ms，10 分钟内不动第二次 |
| `sticky_ttl_secs` | 静态设置 | 成功率 > 98% 且延迟稳定 → 上调（更省请求）；失败率 > 5% → 下调 | 30 ~ 3600s |
| `account_cooldown` | 由错误类型固定（如 Server 600s） | 某账号同类错误在 1h 内重复 ≥3 次 → 冷却时长 ×1.5 | 60 ~ 7200s |
| `pool_weight` | 静态打分 | 用 `ewma_success / ewma_latency` 替换当前权重公式 | 0.1 ~ 10 |

**护栏（红线）**：
1. 只改上面 4 个，永不改协议/鉴权/安全相关；
2. 每次变更写 `app.log` + `evolution_history`（可查、可手动回滚）；
3. 单参数冷却期 10 分钟，全局每小时最多 10 次变更；
4. **自动调参默认关闭**，设置页一个总开关（自用默认关，避免抖动）。

### L3 自修复

- **池内熔断**：连续 N 次失败 → 该池临时权重降到 0，5 分钟后半开探测（单请求试探）；
- **进程级**：网关服务连续异常退出 ≥2 次 → 停止自动重启并在主窗口红条提示（避免无限崩溃循环）；
- **连接池重建**：连续超时集中在同一 host → 重建 ureq/reqwest 客户端。

### L4 本地短路（借 OFM 的 local-optimize）

只做**两类**低风险短路（客户端探测类，语义明确、不影响真实推理）：

| 类型 | 识别 | 本地响应 |
|---|---|---|
| quota 心跳 | `max_tokens <= 1` 且 user 文本含 `quota` | `{ok:true}` 合法响应 |
| 标题生成 | system 含 `title` 且**未声明 tools** | 固定短标题 |

**不做** prefix / filepath / suggestion：那三类误判会破坏 Agent 循环（OFM 自己也强调 near-miss 必须放行）。

### L5 远端规则（暂不做）

OFM 的 `feed/` + `integrity` + `provenance` 适合"多用户分发"，我们是单机自用，收益低、风险高（远端配置 = 新的攻击面）。**暂不实现**，只在文档保留。

## 4. 能力矩阵（独立小工具，不强依赖）

OFM 的 `availability-matrix` 思路可借鉴，但我们要控成本：

- **默认不跑**（探测会消耗真实额度）；
- 触发方式：设置页按钮「探测上游能力」/ 新增账号后一次；
- 探测内容：`tool_calling`（是否返回 tool_calls）、`reasoning`（是否给 reasoning_content）、`max_tokens`（能否吃 8k）、`latency_p50`；
- 每次探测用 `max_tokens: 16` + 固定 prompt，结果写 `kv: capability_matrix`；
- 消费方：路由时若请求带 tools，优先选 `tool_calling=true` 的池（避免"接了工具就报错"）。

## 5. 分期与工作量

| 期 | 内容 | 人日 | 可验证点 |
|---|---|---|---|
| P1 | L1 观测层（内存 + 落盘 + 设置页只读面板） | 1.5 | 发 10 个请求后能在面板看到成功率/延迟 |
| P2 | L2 自适应（4 参数 + 护栏 + 开关 + 历史回滚） | 2 | 手动制造失败，观察参数在边界内收敛 |
| P3 | L3 熔断与半开探测 | 1 | 断网/停上游，池权重自动归零并恢复 |
| P4 | L4 本地短路（quota/标题两类） | 0.5 | 客户端探测请求不再打到上游 |
| P5 | 能力矩阵按钮 | 1 | 探测结果落库，路由按 tools 能力过滤 |

## 6. 风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 自动调参抖动 | 指标噪声导致参数反复横跳 | EWMA + 冷却期 + 每小时变更上限 + 默认关闭 |
| 观测开销 | 每请求多一次加锁 | 无锁分片计数（每池一个 AtomicU64 组），秒级汇总 |
| 短路误判 | 把真实请求当探测请求 | 只做两类高置信规则，undefined 行为一律放行 |
| 探测耗额度 | 每个账号 1 次小请求 | 默认关闭 + 手动触发 + 结果缓存 7 天 |
| 参数漂移不可解释 | 半年后没人记得为什么是这个值 | 每次变更记录「触发规则 + 指标快照」 |

## 7. 验收标准（整体）

1. 关掉自动调参时，行为与现在**完全一致**（零回归）；
2. 打开后连续跑一天，成功率与 P95 延迟不劣于基线（允许 ±3%）；
3. 任一参数变更都能在历史里看到「为什么变」，并能一键回滚；
4. 网关崩溃/断网后，能在 5 分钟内自愈或明确提示，而不是静默卡死。

> 实现顺序建议：P1 先落地（只观测、不决策，零风险），拿到真实数据后再做 P2；否则自适应参数没有数据支撑，调出来也是猜的。
