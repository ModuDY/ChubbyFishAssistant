# 网关「自我进化」方案（P1 已完成，P2 起待实现）

> 状态：P1 观测层已落地（`eed87e1`，2026-10-20）；本稿为 2026-10-22 调研后的修订版
> 关联：`AGENT.md` §5（网关调度）、`docs/pending/桌宠结合设计方案.md`
> 参考实现：OFM、LiteLLM Router、Portkey、Envoy Outlier Detection、Netflix concurrency-limits、Google SRE

## 1. 先澄清「自我进化」是什么

不是让 AI 改自己的代码，也不是训练模型，而是让**网关的策略参数**具备闭环：

```
观测（真实请求结果）
   ↓
影子计算（只给建议，不生效）
   ↓
执行（带边界/步长/冷却的热更新）
   ↓
评估（与基线比，劣化自动回滚）
   ↓
固化（落库，重启沿用；可一键还原）
```

一句话：**用真实数据把「调参」从手工变成自动，并且每一步都能解释、能回滚。**

### 边界（红线）

1. 只动「性能/健康」类参数，永不动协议、鉴权、模型白名单、账号归属；
2. 只在本机决策，不上传任何指标（OFM 的远端 feed 我们不抄，见 §7 L6）；
3. 数据不足时**宁可不动**：低样本下的「自动」等于随机；
4. 默认关闭，手动开关 + 影子模式双保险；
5. 任何一次变更都必须留下「触发规则 + 样本量 + 指标快照」。

### 2.2 缺口（本方案要补的）

| # | 缺口 | 影响 |
|---|---|---|
| 1 | 指标只到「池」，没有「账号」维度 | 无法判断是某个账号坏了还是整个池坏了 |
| 2 | 没有 5m / 1h 时间窗，只有累计 + α=0.05 的 EWMA（≈最近 20 次） | 低 QPS 下「最近 20 次」可能是好几天，决策失真 |
| 3 | 不区分错误来源：上游 5xx / 429 / 超时 / 客户端主动断开都进同一个 `fail` | 客户端取消会误伤账号健康度（Envoy 的 `split_external_local_origin_errors` 正是为此） |
| 4 | 没有首字延迟（TTFT）、对冲命中率、429 率等决策信号 | 对冲阈值、并发上限无法闭环 |
| 5 | 指标只在内存，重启即清零 | 无法做跨天/跨周的效果评估 |
| 6 | 没有任何「建议→应用→历史→回滚」模块 | 全靠手改设置 |
| 7 | `metrics.record` 每请求加一次全局锁 | 当前 QPS 可接受，观测 2.0 顺手改成按池分片 |

## 3. 外部参考：借什么、不借什么

| 来源 | 核心机制 | 我们借用的部分 | 明确不借 |
|---|---|---|---|
| **Envoy Outlier Detection** | 连续 5xx 剔除、成功率离群剔除、`base_ejection_time × 连续剔除次数`、`max_ejection_percent` 防止全剔 | ① 本地/上游错误分离；② 成功率统计**必须有最小请求量**才判定；③ 冷却时长按连续次数递增（我们已实现）；④ 永不剔光（我们已有 busy_fallback） | 主动健康检查集群、按主机维度的 stdev 剔除（账号只有几十个，统计意义不足） |
| **LiteLLM Router** | `allowed_fails` + `cooldown_time`、fallbacks、`enable_weighted_failover`（先同组换部署再跨组）、health-check driven routing | ①「先池内换号，再跨池」的优先级；② 冷却时间与健康检查间隔的约束关系（冷却必须长于探测间隔） | Redis 共享状态、多实例调度（我们是单机单进程） |
| **Portkey** | 权重归一化、sticky（`hash_fields` + TTL）、策略可组合（负载均衡里套 fallback） | ① 粘性键用「会话 id / 消息指纹」而不是账号；② 策略分层：选池 → 选号 → 回退，不混在一起 | 云端控制面、条件路由 DSL |
| **Netflix concurrency-limits** | 用 Little's Law 估并发；AIMD / Vegas / Gradient2 自适应限流 | **账号并发上限用 AIMD**：遇 429 乘性减，连续干净窗口加性增 | 复杂 Vegas/Gradient2（需要稳定 RTT 基线，免费上游噪声太大） |
| **Google SRE「Handling Overload」** | 客户端自适应拒绝概率、拒绝要比排队更划算 | ① 过载时快速失败而不是无限重试；② 拒绝/降级要有明确指标 | 客户端拒绝概率公式（我们是本机单用户，不需要主动拒绝） |
| **RouteLLM（LMSYS）** | 用偏好数据训练「强/弱模型」路由器，省成本 | 只借「路由是一个可评估的决策问题」这一思路 | 学习型路由：需要标注偏好数据与训练管线，我们的目标是**健康度**不是回答质量 |
| **OFM（dsh-our-free-model）** | 可用性矩阵探测、本地短路、分钟级速度统计、跨池接力、自愈 | ① 本地短路两类高置信规则；② 能力矩阵改为「被动优先」；③ 分钟级统计 | 远端规则下发 + 签名校验（单机自用收益低、攻击面大） |

> 结论：**我们缺的不是「更聪明的算法」，而是「可信的观测 + 有纪律的动作」**。在单机、低 QPS、免费额度的场景里，规则 + 边界 + 回滚比机器学习更稳。

## 4. 设计原则（从上面案例提炼）

1. **样本门槛**：一个窗口少于 20 个请求，不做任何决策；对冲类信号少于 5 次，不调阈值。
2. **本地错误不算上游的账**：客户端断开、用户取消、网关自身超时单独计数，不进入成功率与权重。
3. **有界动作**：每个参数有硬上下界 + 单次步长上限；一次只动一个参数。
4. **迟滞**：新值与旧值差异小于阈值（如 5%）不写入，避免抖动。
5. **冷却与预算**：单参数 30 分钟内最多改一次；全局每小时最多 6 次；回滚后该参数冻结 60 分钟。
6. **评估窗口**：变更后观察 30 分钟，与「同时段前 3 小时基线」比较，而不是与全天平均比（避开昼夜差异）。
7. **可解释**：历史记录必须包含规则 ID、样本量、窗口快照；没有这三样视为 bug。
8. **默认不自动**：总开关默认关；打开后先跑影子模式。

## 5. L1.5 观测 2.0（P2 的地基）

### 5.1 数据结构

按 `(pool, uid)` 维护，同时保留池级汇总：

```text
SeriesKey = "trae:uid-xxx" | "wb:-"（池汇总）
MinuteBucket = {
  minute_ts: i64,
  ok: u32, upstream_5xx: u32, timeout: u32, rate_limited: u32,
  auth: u32, local_abort: u32,
  ttft_hist: Hist,      // 首字延迟，近似 P50/P95
  dur_hist: Hist,       // 总耗时
  tokens: u64,
  hedge_fired: u32, hedge_won: u32,
}
Ring = 60 个 MinuteBucket（1 小时），读取时聚合 5m / 1h
```

- 直方图用**对数分桶**（24 桶，50ms–64s），P50/P95 误差 < 5%，单序列内存 < 1KB；
- 不用「每请求存样本」的数组，避免长跑内存膨胀；
- 记录入口改为 `record(pool, uid, outcome, ttft_ms, duration_ms, tokens, hedge)`。

### 5.2 错误分类映射

复用现有 `ErrKind`，新增一个「归因层」：

| 归因 | 来源 |
|---|---|
| `upstream_5xx` | Server、网关 502/503/504 |
| `rate_limited` | SoftRate、PlanLimit、429 |
| `auth` | Forbidden、SessionDead、refresh_token_invalid |
| `timeout` | 首字超时、读超时 |
| `local_abort` | 客户端断开、请求被新请求取消、服务停止 |
| `ok` | 正常完成 |

`local_abort` **不计入**成功率、权重、冷却；只用于排查。

### 5.3 落盘

- 每 60s 汇总一次写入 SQLite 新表 `evolution_metrics`：
  `(minute_ts, pool, uid, ok, upstream_5xx, timeout, rate_limited, auth, local_abort, p50_ttft, p95_ttft, p50_dur, p95_dur, tokens, hedge_fired, hedge_won)`；
- 保留 7 天（`api_usage` 是 90 天，这里是决策数据，不需要那么长）；
- 写入失败只记日志，不阻断网关；
- 重启后从最近 60 分钟回填环形缓冲，避免「刚重启没有基线」。

### 5.4 插桩点（已核对代码）

| 位置 | 改动 |
|---|---|
| `api_server/mod.rs` `record_usage_ttfb` / `record_usage_custom` / doubao / qoder | 把 `uid`、`ErrKind`（或 outcome）、`hedge` 结果一起传给 `metrics.record` |
| `api_server/wb_upstream.rs` `lines_with_first_byte_hedged` | 回传 `hedge_fired/hedge_won`（谁先出首字） |
| `api_server/pool.rs::note_error` | 保持冷却逻辑不变，只把本次错误归因写进观测（单一事实来源） |
| `commands/evolution.rs` | 新增 `evolution_metrics_v2`（窗口聚合）与 `evolution_history`（历史） |

### 5.5 开销目标

- 单次记录 < 10µs，不新增网络请求；
- 每池一把锁 + 每账号一个 `Arc<Mutex<Ring>>`，取号后释放全局 map 锁；
- 每分钟落盘一次，单次写入 < 20 行。

## 6. L2 自适应（P3）

### 6.1 只允许自动调整这三项

| 参数 | 现值 | 决策信号 | 规则（有界） | 最小样本 | 冷却 |
|---|---|---|---|---|---|
| `account_concurrency_limit`（per pool） | 1 | `rate_limited` 率、p95 TTFT | **AIMD**：出现 429/PlanLimit → `limit-1`（下限 1，立即）；连续 30 分钟无 429 且 p95 TTFT ≤ 基线×1.2 → `limit+1`（上限 4） | 3 次请求 | 10 分钟 |
| `hedge_threshold_ms`（per pool） | 8000（运行时 clamp 1–8s） | 对冲触发率、对冲胜率、p95 TTFT | 胜率 < 20% 且触发 ≥ 5 次 → 阈值 +1000ms；p95 TTFT > 基线×2 且胜率 ≥ 40% → 阈值 −1000ms | 5 次对冲 | 30 分钟 |
| 权重公式（不是设置项） | 积分×10 + 闲置 + 成功率×3 | EWMA 成功率、相对延迟 | `score' = score × m`，`m = clamp(0.7 + 0.6×ewmaSuccess − 0.3×min(latencyRatio,2), 0.7, 1.3)`；仅对「有积分、非冷却、非禁用」账号生效 | 20 次请求 | 5 分钟重算，变化 < 0.05 不写 |

补充约束：

- 对冲率硬上限：`hedge_fired / requests ≤ 10%`，超过则先抬高阈值，不看胜率；
- 并发上调只在「该账号最近 30 分钟没有被 429」时进行；
- 权重乘子**不得覆盖积分因子**：积分耗尽的账号仍然优先退出，不因成功率高而被继续使用；
- 所有参数写入 `api_pool.json` 前先 clamp，非法值回退默认；
- 设置页每个自动参数旁显示「当前值 / 建议值 / 上次变更时间 / 触发原因」。

### 6.2 明确不自动调整（原因）

| 参数 | 为什么不 |
|---|---|
| `sticky_ttl` / 池粘性 | 收益来自上游 KV cache，无法直接观测；自动调可能白丢缓存 |
| 冷却时长（PlanLimit/Server/SessionDead） | 安全语义，误调会导致账号被反复打爆或长期闲置 |
| 池开关 / 回退策略 / 白名单 | 属于用户意图，不是性能参数 |
| 模型路由（降级档位） | 影响回答质量，应由用户设置决定 |

### 6.3 影子模式（先跑 7 天）

- 每次窗口结算只计算「建议值」，写入 `evolution_history`，`applied=false`；
- 面板展示「如果当时应用会怎样」：建议变更次数、方向分布、是否反复横跳；
- 只有影子记录中「单参数 24h 内建议变更 ≤ 2 次」时，才允许打开自动应用。

### 6.4 评估与回滚

变更后 30 分钟为观察窗，基线取「同时段前 3 小时」的池级指标：

| 触发条件（满足任一，且样本 ≥ 20） | 动作 |
|---|---|
| 上游成功率下降 > 3pp | 回滚该参数，冻结 60 分钟 |
| p95 TTFT 上升 > 25% | 回滚 |
| `rate_limited` 率翻倍 | 回滚 |
| 回滚后再次劣化 | 该参数本次运行期禁用，面板红条提示 |

历史表 `evolution_history`：

```text
{ id, ts, pool, param, old, new, rule_id, samples, snapshot_json,
  applied, shadow, rollback_at, rollback_reason }
```

## 7. L3~L6

### L3 自愈（P4）

- **任务级守护**：网关是 Tauri 进程内的 axum 服务（非独立进程），崩溃表现为任务退出/端口不再监听。守护逻辑：检测到退出 → 1s/5s/30s 退避重启；10 分钟内 3 次失败 → 停止自动重启 + 主窗口红条。
- **半开单飞**：账号或模型冷却到期后，只放行 1 个试探请求（`AtomicBool`），其余请求继续走回退；成功才恢复权重，失败继续冷却。避免「到期瞬间所有请求一起打过去」。
- **连接池重建**：同一 host 5 分钟内连续 5 次超时 → 重建 reqwest client（只重建客户端，不动账号状态）。
- **冷却抖动**：所有冷却结束时间加 ±10% 随机抖动，避免多账号同一秒恢复。
- **panic 语义**：保留现有 busy_fallback；任何情况下「有账号就至少尝试一次」，不因全冷却直接 503。

### L4 本地短路（P5）

只做两类，且必须「宁放过、不误判」：

| 类型 | 识别条件（全部满足） | 本地响应 |
|---|---|---|
| quota 心跳 | `max_tokens ≤ 1`、非流式、无 tools、messages ≤ 2、文本匹配 `quota/额度/配额` | 合法 OpenAI 形状 `{choices:[{message:{content:"ok"}}]}` |
| 标题生成 | system 含 `title/标题`、无 tools、非流式、prompt < 2k 字符 | 固定短标题（取首条用户消息前 12 字，失败则 "新对话"） |

- 任一条件不满足 → 原样转发（near-miss 放行）；
- 短路计数与「省下的 token」进观测面板；
- 不做 prefix / filepath / suggestion 三类：误判会破坏 Agent 循环。

### L5 能力矩阵（P6，被动优先）

- **被动学习**：每次真实请求记录「模型 × 能力」结果：tools 请求是否成功、是否返回 `reasoning_content`、长上下文是否 400、图片输入是否被拒；
- 每模型每能力样本 ≥ 3 才参与路由过滤；
- 7 天过期，避免上游升级后画像陈旧；
- 设置页保留「主动探测」按钮（`max_tokens: 16` 固定 prompt，手动触发，结果缓存 7 天），默认不跑。

### L6 远端规则（不做）

OFM 的 `feed/` + `integrity` + `provenance` 适合多用户分发；单机自用收益低，且远端配置是新的攻击面。文档保留结论，不进入排期。

## 8. 分期与验收

| 期 | 内容 | 可验证点 |
|---|---|---|
| **P1.5 / P2-a** | 观测 2.0：账号维度、5m/1h 窗口、错误归因、TTFT/对冲计数、SQLite 落盘、面板 v2 | 发起 30 个请求（含 1 次取消、1 次 429）后：面板能分别看到「上游失败 / 限流 / 本地取消」，重启后最近 1 小时数据仍在 |
| **P2-b** | 影子建议：3 个参数的规则 + 历史表，只写不应用 | 连续运行 24h，历史中出现建议记录且 `applied=false`；单参数建议变更 ≤ 2 次/天 |
| **P3** | 自动应用：总开关（默认关）、边界/步长/冷却、评估与自动回滚 | 手动制造 429 风暴 → 并发上限降到 1；恢复后 30 分钟回升；人为注入劣化指标 → 自动回滚并留下原因 |
| **P4** | 自愈：任务守护、半开单飞、连接池重建、冷却抖动 | 杀掉监听端口 → 10 分钟内自动恢复或红条提示；停上游 → 冷却到期只发 1 个试探 |
| **P5** | 本地短路两类 + 计数 | 客户端 quota 心跳不再产生上游请求；普通请求零误判（回归测试） |
| **P6** | 能力矩阵（被动） | tools 请求自动避开不支持 tools 的模型；无样本时行为与现在一致 |

### 单测清单（Rust）

- `series_windows_aggregate`：60 个分钟桶 → 5m/1h 聚合正确；
- `local_abort_excluded_from_success_rate`：取消请求不影响成功率；
- `min_sample_guard_blocks_decision`：样本 < 20 时不产生建议；
- `aimd_clamps_concurrency`：429 连发时不低于 1，干净窗口不超过 4；
- `hedge_threshold_step_and_bounds`：步长 1000ms、边界 1–8s、胜率规则；
- `weight_multiplier_bounded`：乘子始终在 0.7–1.3，冷却/禁用账号乘子为 0；
- `rollback_triggers_on_degradation`：成功率 -3pp / p95 +25% / 429 翻倍分别触发；
- `history_records_rule_and_snapshot`：历史必含 rule_id 与样本快照；
- `params_clamped_on_load`：脏配置不会产生越界值。

## 9. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 低样本误判 | 免费池一天可能只有几十个请求 | 最小样本门槛 + 影子模式 + 建议变更频率上限 |
| 指标被客户端污染 | 用户主动取消被记成上游失败 | `local_abort` 独立归因，不参与决策 |
| 参数抖动 | 指标噪声导致反复横跳 | 迟滞（5%）、步长上限、冷却、回滚后冻结 |
| 免费额度被对冲吃掉 | 对冲请求同样消耗额度 | 对冲率 ≤ 10%，胜率低时优先抬阈值 |
| 观测开销 | 每请求加锁/落盘 | 分片锁 + 分钟聚合 + 异步落盘 |
| 半年后不可解释 | 没人记得参数为何变成这样 | 历史表强制记录规则 ID、样本量、指标快照 |
| 上游策略变化 | 免费车道随时改限额 | 能力画像 7 天过期；参数边界不依赖具体额度数值 |

## 10. 待决策（实现前需要拍板）

1. **自动应用默认关还是开？** 建议默认关，只开影子；连续 7 天影子稳定后再由用户手动打开。
2. **观测落盘保留多久？** 建议 7 天（与决策窗口匹配），不占用 `api_usage` 的 90 天。
3. **权重公式是否进入首批自动项？** 建议先影子两周；首批只自动「并发上限 + 对冲阈值」，这两项影响可逆且容易观测。
